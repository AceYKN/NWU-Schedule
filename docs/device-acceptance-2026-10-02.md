| 场景 | 实际观察 | 结论 |
| --- | --- | --- |
| 大量提醒计划 | Flutter 从合成课表生成 708 条未来提醒；原生保存 708 条，仅激活最近 64 条 | 通过；超过 500 条未被整体截断 |
| 通知权限关闭 / 恢复 | 撤销权限后设置显示“系统通知已关闭”；恢复后显示允许 | 通过；测试后权限恢复允许 |
| 提醒渠道关闭 / 恢复 | 系统渠道页关闭后，返回 App 显示“提醒渠道已关闭”，同时保留系统权限允许状态；再开启后恢复 | 通过；测试后渠道恢复允许 |
| 真正重启、不开 App | 设备重启后，系统恢复广播最终触发原生恢复；完整计划过滤已过期的 3 条，保留未来 705 条，激活 64 条，未出现补排失败标记 | 恢复路径通过；存在下文所述模拟器启动延迟 |
| 覆盖安装、不开 App | 使用 `adb install -r` 触发真实 `MY_PACKAGE_REPLACED`；合成加速计划恢复 | 通过；未伪造受保护系统广播 |
| 后台送达与补排 | 705 条计划中加速的 3 条实际出现在系统通知栏；余量变为 702，激活数维持 64，第 65、66、67 条进入窗口，补排失败为 false | 通过；额外的 Android 自动分组摘要不算重复提醒 |
| 点击通知 | 点击系统通知栏中的合成提醒，进入对应独立 ADD 的课程详情 | 通过 |

为在合理时间内验证原生送达，测试辅助脚本把前三条原生计划的触发时间调整到几分钟后，保留真实 AlarmManager、Receiver、通知栏及补排逻辑。此项是加速原生链路验收，不能等同于观察整个学期 708 次送达；课表到完整计划的计算另由 Flutter 和原生自动化验证覆盖。

重启过程中观察到 `com.android.systemui` ANR（17:54:14），启动广播在系统 offload 队列中等待，恢复接收器未立即执行。系统广播恢复执行后排程恢复成功；为恢复交互重启了模拟器 SystemUI 进程。本轮没有把这一现象记为 NWU App ANR，也没有据此保证正常设备重启时的恢复耗时。提醒仍使用普通 AlarmManager，不能保证准点；本次实际通知送达不属于强制 Doze 下的通知测试。

本次发现并修复两处真实问题：Small 在大字体下仍显示全部辅助行，导致底部信息被裁切；Small 的整卡点击固定进入首页。现按可用高度分配标题行数、标签、时间和上下内边距，不修改字体大小；有下一节时点击进入该课程，无下一节时进入首页。新增原生高度预算回归，13 项 Android 测试全部通过，并重新构建和安装上述 APK。
